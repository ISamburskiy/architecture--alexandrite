**Мотивация**
Существует проблема зависания заказов в непонятном статусе, а также "потери сообщений". Трейсинг позволит понять причины этого, что поможет их быстро устранять - таким образом будет зависать и теряться меньше заказов. В результате ожидаем:
- уменьшение числа потерянных заказов
- более быстрый trouble-shooting
- удобный поиск узких мест в жизненном цикле заказа

**Предлагаемое решение**
Вводим систему трейсинга запросов. На первом этапе делаем на этапах, когда идет взаимодействие между сервисами, т.к. там вероятнее зависания из-за ошибок интеграции и потери. То есть с этапа SUBMITTED по этап MANUFACTURING_STARTED. Потом по необходимости расширяем на весь жизненный цикл заказа.

В spans указываем order_id, чтобы по нему можно было легко найти всю информацию.

Реализуем через OpenTelemetry и Jaeger. Добавляем их в деплой и дорабатываем сервисы:
- Shop API
- MES API
- CRM API
- Message Queue

**Компромиссы**
Пока что применяется только для отслеживания причин зависания заказов в неконечных статусах из-за ошибок или потерь сообщений. Для других ситуаций трейсинг пока не выглядит целесообразным.

**Доступ в систему трейсинга**
Для доступа в систему настраивается специальная техническая учетная запись. Credentials учетной записи сообщаются сотрудникам, которые будут использовать трейсинг для trouble-shooting-а, если более строгих требований уже не предусмотрено политикой компании по информационной безопасности.
